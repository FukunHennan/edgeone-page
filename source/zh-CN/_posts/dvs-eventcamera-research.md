事件相机（Dynamic Vision Sensor, DVS）与传统全局曝光相机工作方式完全不同：它不是按帧输出图像，而是异步输出每个像素的亮度变化事件。这种机制带来高时间分辨率、低延迟、低功耗，但也意味着传统基于帧的视觉算法不能直接套用。本文记录使用 DVS 开展研发的工程实践。仓库地址：[FukunHennan/DVS-Eventcrame](https://github.com/FukunHennan/DVS-Eventcrame)。

## 事件相机与传统相机的本质区别

传统相机输出的是"每个像素在曝光时间内的亮度积分"，事件相机输出的是"每个像素亮度变化达到阈值时的事件流"。事件包含四元组 `(x, y, t, polarity)`：像素位置、时间戳（微秒级）、极性（亮度上升 ON 或下降 OFF）。

这种差异决定了处理流程的根本变化：你不能再用 `cv2.imread` 读取一帧，而要把事件流按时间窗口聚合为"事件帧"或"时间表面"，再交给下游算法。事件相机的强项是高速运动、低延迟、低光照、低功耗，弱项是静态场景几乎没有事件输出。

## 数据流与 SDK 封装

研发阶段最容易踩的坑是直接调 SDK API 写算法，结果换一台相机或换一版固件就要重写大段代码。我把事件相机相关代码分成两层：

- **设备层**：封装 SDK 的枚举、连接、配置、启动、停止、释放，对外只暴露 `start()`、`stop()`、`get_events()` 等接口；
- **数据层**：把事件流按时间窗口或事件数量聚合，输出事件帧、时间表面或原始事件，供算法层消费。

这样算法层不关心具体硬件型号，只关心聚合后的数据结构。后续接入不同厂商的 SDK 时，只需要替换设备层实现。

## 录制与回放

事件相机的实验非常依赖数据集：相同实验条件难以复现，必须把事件流录制到磁盘并在离线状态下反复测试算法。我设计的录制格式是简单的二进制：每个事件 16 字节（4 字节 x、4 字节 y、8 字节时间戳、1 字节极性、3 字节保留），按时间顺序追加写入。

回放时按时间戳回放，模拟实时数据流，便于评估算法的延迟特性。回放器可以调节速度（1x、0.5x、2x），也能跳转到指定时间点，对算法调试非常有用。

## 与 RGB 相机的多模态融合

DVS 的强项是高速运动，RGB 相机的强项是纹理与色彩。把两者融合可以同时获得高时间分辨率和丰富语义信息。这个仓库的研发成果会直接进入 [DVSenseRealtime_RGB_Hikrobot](https://github.com/FukunHennan/DVSenseRealtime_RGB_Hikrobot) 工作站，这里主要记录融合前的数据流设计。

融合的关键约束是时间同步：DVS 事件流没有"帧"概念，RGB 帧有固定时间戳。我把 RGB 每帧时间戳作为锚点，从 DVS 事件流中截取 [t-Δ, t] 的时间窗口，聚合为事件帧，与 RGB 帧对齐。Δ 的选择取决于运动速度：运动越快，Δ 越小，否则事件会糊在一起。

几何对齐则是另一个独立问题：需要先做 DVS 和 RGB 的双目标定，得到内外参，再根据深度信息做投影。这部分在多模态视觉工作站仓库里有详细记录。

## 实验设计与评估

事件相机算法评估要避免几个常见错误：

- **不要用平均 FPS 评估**：事件相机没有"每秒帧数"概念，应该用"每秒事件数"、"处理延迟"、"漏事件率"评估；
- **要在不同光照下测试**：DVS 对光照变化非常敏感，同一场景在不同光照下事件数量差异巨大；
- **要保留原始事件流**：聚合后的数据集已经损失信息，必须保留原始事件流以便后续尝试新算法；
- **要记录实验条件**：光源、距离、运动速度、温度，这些都会影响事件输出。

## 小结

DVS 事件相机研发最容易卡住的不是算法，而是工程化：SDK 封装、数据流、录制回放、时间同步、实验记录。把这些做扎实，后续无论是动作识别、目标跟踪还是高速测量，都能快速迭代。这个仓库是 DVS 研发的工程基础，与多模态视觉工作站互补使用。
