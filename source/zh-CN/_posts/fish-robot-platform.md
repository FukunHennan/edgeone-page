Fish 将机器鱼控制、赛事管理与实时视频接入同一平台。文章按实际开发顺序，梳理功能目标、技术选型、设备通信、公网访问、视频传输与赛事录像，重点说明技术方案与实现思路，不展示具体界面和运行效果。

**搭建路线**：确定服务分工 → 建立网页与 ESP32 的控制通道 → 通过 Tunnel 提供公网网页入口 → 接通直连、TURN 与快照视频路径 → 完成比赛录像、回放和下载。

文中的“当前实现”以 2026 年 10 月核对的 Fish 代码为准；后续迭代不自动反映在本文中。

## 平台目标与功能

| 使用者 | 主要能力 |
| --- | --- |
| 选手 | 控制已分配的机器鱼，观看比赛画面 |
| 裁判 | 分配设备、计时计分、调整画面、录像与回放 |
| 管理员 | 管理设备状态与固件升级 |

平台由浏览器、Go 控制服务、ESP32 固件和 Python 视频服务组成。控制指令、网页请求与视频媒体各有传输路径，因而需要分别设计访问、连接维护和故障处理。

## 一、系统分工与技术选型

![浏览器、Go、ESP32 与 Python 的请求和媒体路径](/projects/fish/frontend-backend-flow-zh.svg)

| 部分 | 当时的选择 | 选择依据 |
| --- | --- | --- |
| 控制服务 | Go | 正在学习 Go，希望借项目尝试服务器开发；此前缺少同类项目经验 |
| 视频服务 | Python | 已有可用的 Python 视频工具，可以沿用相机与视频处理代码 |
| 网页前端 | 原生页面与 React 并存 | 当时缺少前后端项目经验，初始方案主要参考 AI 建议 |

### 前后端技术如何分工

| 技术 | 在 Fish 中的作用 | 需要分清的边界 |
| --- | --- | --- |
| 原生 HTML、CSS、JavaScript | 构成赛事页，处理界面交互、控制消息和视频播放 | 页面逻辑直接依赖 DOM，功能增长后需控制事件、状态与样式的分散程度 |
| React | 将管理台界面拆成组件，并管理组件状态与数据流 | 只用于管理台，不代表整个前端都由 React 实现 |
| Vite | 为两类前端页面提供开发和构建流程 | 它是构建工具，不能代替界面框架或解决状态组织问题 |
| Go | 提供 HTTP 接口与控制连接，维护账号、设备归属、控制权和比赛状态 | 负责权限与指令调度；正常 WebRTC 视频媒体不由 Go 转发 |
| Python | 沿用现有相机与视频工具，通过基于 asyncio 的 aiortc 提供 WebRTC 轨道，并在主机端录像 | 不要把浏览器播放状态当作录像状态 |

ESP32 固件执行运动，并保留独立的本地停止能力。赛事页与管理台采用不同的界面组织方式，增加了样式与交互维护成本。

**事后建议**：现阶段保留已有的原生赛事页和 React 管理台，不为统一框架整体重写。先统一颜色、间距等样式变量，并把控制状态、网络请求和视频播放从页面 DOM 操作中拆成独立模块；新增管理功能沿用 React。若赛事页继续增长，且跨页面状态与交互复用成为主要负担，再评估逐步迁移。页面加载时间与视频首帧时间应分别测量，不能仅凭框架选择判断性能。

## 二、网页与 ESP32 的通信

浏览器不直接连接机器鱼。浏览器和 ESP32 分别与 Go 保持 WebSocket 连接：Go 核验账号、设备归属和控制权，再向设备转发指令；设备向 Go 回传状态与遥测信息。

![浏览器、Go 和 ESP32 的控制消息与断线恢复流程](/projects/fish/communication-lifecycle-zh.svg)

| 环节 | 当前实现 | 断线或超时时 |
| --- | --- | --- |
| 浏览器 → Go | HTTP 完成登录与设备绑定；控制指令走同源 `/ws/control`，设备状态通过 SSE 更新 | 重连控制 WebSocket；控制权失效后须重新取得租约 |
| ESP32 → Go | 设备主动连接 `/ws/device`，经随机挑战与 HMAC 证明身份；指令和状态采用 JSON | 固件停止运动，并尝试重新连接、注册 |
| 连接维护 | Go 对 WebSocket 使用 Ping/Pong；设备另发送应用心跳与状态 | 超时连接关闭，设备被标记为离线 |
| 运动准入 | Go 检查控制租约、指令顺序与有效期；固件检查动作有效期 | 清除旧运动并排入 STOP；固件可独立执行本地停止 |

连接仍然存活，不代表旧运动指令应继续执行。设备连接超时与动作有效期是两道边界：网络故障尚未被正式判定时，过期动作也应先停止；浏览器重连后仍须通过控制权校验。

![运动指令从浏览器到 ESP32 的准入与停止流程](/projects/fish/control-flow-zh.svg)

新增控制入口时，应复用 Go 的统一准入逻辑，保留队列过期、STOP 和固件本地停止机制。固件的安全停止会使摆动停止并回到中位角度，不等于切断舵机电源。

## 三、前端访问路径与公网入口

Fish 部署在本地计算机上。项目已有可长期使用的域名，但主机缺少可供外网直接访问的公网 IP，外网用户最初无法打开网页，也无法观看实时视频。这里先解决浏览器如何加载前端页面、调用接口并交换信令；视频画面另走下一章的媒体路径。

![外网浏览器经 Cloudflare Tunnel 到达 Go 网页入口](/projects/fish/public-access-zh.svg)

| 前端内容 | 传输路径 |
| --- | --- |
| 页面与静态资源 | 浏览器 → 长期域名 → Cloudflare → Tunnel → Go；Go 返回 HTML、CSS 和 JavaScript |
| HTTP 接口与信令 | 浏览器沿同一入口请求 Go；WebRTC offer/answer 经 HTTP 接口交换，Go 调用本机 Python API |
| 控制 WebSocket | 浏览器沿同一入口连接 Go 的 `/ws/control`；JPEG 降级也复用同源入口 |

Fish 主机上的 cloudflared 主动建立 Tunnel，使已有域名成为稳定的网页入口，无须依赖可供入站访问的公网 IP。该入口承载网页、接口、控制消息与信令；正常 WebRTC 视频媒体不经过 Go，也不经 Tunnel 转发。网页能够打开，只证明前端入口可用，不能证明视频能够直连。

## 四、视频媒体路径与降级

外网访问端最初无法直接访问运行 Go/Python 视频服务的 Fish 主机。前端访问路径建立后，视频仍须从相机所在主机传到浏览器；这里的“设备”指 Fish 主机，不是 ESP32 机器鱼。

Python 采集相机画面，并通过 aiortc 提供 WebRTC 视频轨道。浏览器经 Go 的 HTTP 接口交换连接描述，实际媒体优先尝试直连，失败后尝试 TURN。两条 WebRTC 路径都不可用时，Go 通过同源 WebSocket 转发 JPEG 快照。

### WebRTC 为什么需要信令与 ICE

| 建连环节 | 通用原理 | Fish 中的对应方式 |
| --- | --- | --- |
| 信令 | 双方先交换 offer/answer 等连接描述；WebRTC 不规定必须用哪一种信令传输方式 | 浏览器经 Go 的 HTTP 接口与 Python 交换连接描述，网页入口负责协商，不承载正常视频媒体 |
| ICE 连通性检测 | 双方收集候选地址，检查哪条网络路径能建立连接；TURN 可在直连不可用时中转 | 当前先尝试仅含 host 候选的直连，再单独尝试仅含 relay 候选的 TURN |
| 媒体传输 | 建连后，浏览器通过 WebRTC 视频轨道接收画面 | 仍需检查首帧和后续更新；仅有连接状态不能证明画面持续可用 |

这三个环节解释了为什么“网页能打开”与“视频能播放”是两项独立检查。直连与 TURN 的先后尝试是 Fish 当前的选路设计，不是 WebRTC 对所有应用规定的顺序。

![WebRTC 信令与直连、TURN、JPEG 三条视频媒体路径](/projects/fish/media-path-zh.svg)

项目当时处于试验阶段，保留独立的 TURN 路径也为了观察中转效果；它是直连失败后的尝试，不表示中转一定更快。

### 直连如何判定

若能取得访问者 PC 与 Fish 主机的内网地址，比较 IP 和子网掩码可以提供“可能同网段”的线索，但不能证明媒体可达。经 Tunnel 访问时，Go 也无法从网页请求的来源还原 PC 的内网 IP。当前程序不以 IP 比较选路，而是检查 ICE 连接、首帧到达及后续画面更新。

![浏览器与 Fish 主机的视频直连可达性判断](/projects/fish/lan-reachability-zh.svg)

### 失败如何降级

![直连失败后依次尝试 TURN 与 JPEG 快照的流程](/projects/fish/video-fallback-zh.svg)

连接失败或中断、视频轨道结束、解码错误、首帧超时及持续停帧，都会触发下一阶段。JPEG 快照是为 WebRTC 不可用时保留的最终兜底：Go 从 Python 取得帧，只向浏览器发送更新后的 JPEG；快照 WebSocket 断开后会重连。它增加了一条可用路径，但网页同源连接失效时也无法工作，不能保证绝对稳定。

当前实现是**直连 → TURN → 快照**的顺序降级。进入快照后，同一会话只重连快照流，不会自动升回 WebRTC；持续比较延迟、丢包并切换最优路径仍在开发，不能写成现有能力。

## 五、比赛画面的直播、录制、回放与下载

实时画面供比赛期间观察现场；录像、回放和下载完善了赛后资料链路，用于复盘、争议核查与资料留存。摄像头通过 USB 连接 Fish 主机，Python 已负责采集画面，因此录像从主机上的画面源生成，不从浏览器播放画面反向录屏。

![USB 相机画面分流至直播和主机端录像，录像再供回放与下载](/projects/fish/competition-video-lifecycle-zh.svg)

相机帧经过旋转和选手有效区裁剪后，供直播与服务器录像共用。直播依照上一章的媒体路径传输；录像独立编码为 H.264 MP4，使用真实采集时间写入帧并限制编码帧率，不通过复制帧填补间隔。浏览器 WebRTC 连接异常不等于主机录像停止；录像仍以相机和录制服务的状态为准。

![设备分配、录像启动、比赛暂停与结束回放的状态流程](/projects/fish/competition-flow-zh.svg)

| 环节 | 当前实现 | 需要保留的边界 |
| --- | --- | --- |
| 开始 | 确认可用的真实相机画面；Go 要求 Python 启动录像，成功后才开始计时 | 录像失败时阻止正式开赛 |
| 暂停 | 暂停计时，录像保持连续 | 计时状态与录像状态分开 |
| 结束 | Python 封存 MP4，Go 将录像地址和编码统计写入比赛记录 | 回放依赖封存文件，不依赖直播连接 |
| 回放 | 浏览器经认证的同源 HTTP 接口播放 MP4，可按计分事件定位 | HTTP Range 支持拖动播放；事件须保留时间信息 |
| 下载 | 浏览器从同一接口取得 MP4，再交给浏览器保存 | 当前先将完整文件读入浏览器内存，大文件会增加占用 |

录像与选手比赛画面保持相同构图；录制期间应避免修改旋转角度或有效区。回放、下载经 Go 代理的 HTTP 文件接口，不使用直播的 TURN 链路。
