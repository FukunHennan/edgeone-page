STM32F407 水下机器人航向控制系统：从硬件到上位机

记录基于 STM32F407 的水下机器人航向舵机控制系统的设计取舍：为什么把 159 个参数统一到 Modbus RTU 并把寄存器表当契约、原始九轴数据为什么会把舵机抖坏、以及上位机为什么坚持浏览器直连。

嵌入式

水下机器人最难的不是单个传感器，也不是单段代码，而是把姿态、舵机、Modbus、卡尔曼滤波和上位机界面接成一套能下水的系统。每一部分单独跑都通，一到联调，问题全出在接口上。

本文按这个思路展开：先说三个花了最多时间的判断，再讲系统结构。仓库：FukunHennan/underwater-robot-steering-control-system。

三个判断

先给结论，后面逐条展开：

  1. 协议层不要自己发明。 159 个参数如果各写一套协议，两边实现迟早对不上。统一到 Modbus RTU，并把寄存器表当契约：任何变更都先改表、再改代码、最后改界面。
  2. 原始数据不能直接喂舵机。 九轴原始值噪声大，直接参与补偿会让舵机持续高频抖动。卡尔曼滤波是必需品，而且 Q/R 必须在运行时可调——水流一变，固定参数就不够用。
  3. 上位机不要装软件。 Web Serial API 让浏览器直连串口，现场调试不用带驱动、不用装后台进程。

硬件与接口

主控 STM32F407VET6（168 MHz Cortex-M4），三路串口各司其职：

接口 用途 波特率
USART1 调试串口 115200
USART2 Modbus RTU，下位机为从站 0x01 9600
USART3 ATK-MS901M 九轴传感器 —

引脚分配、电源域与隔离方式记录在仓库 pinout.md，硬件迭代时直接复用。

Modbus RTU：把寄存器表当契约

水下机器人的参数数量很容易失控：姿态、PWM、ADC、气压、磁力计、GPIO、红外、卡尔曼参数、舵机补偿，加起来 159 个。

我最初担心的不是参数多，而是协议表会失控——每个参数单独定义一套协议，表会越写越长，下位机和上位机各实现一遍，联调时对不上号变成常态。所以协议层不自己发明，直接用 Modbus RTU，下位机做从站。

159 个寄存器（0x0000–0x00E8）按功能分 13 组：

功能 地址区间 功能 地址区间
系统 0x0000–0x0005 ADC 校准 0x0056–0x006B
姿态 0x0010–0x001B GPIO 0x006C–0x0077
PWM 0x0020–0x0029 红外 0x0078–0x007F
ADC 0x0030–0x0039 卡尔曼 0x0086–0x009E
PWM 频率 0x0040–0x0047 舵机补偿 0x00A0–0x00DF
气压计 0x0048–0x004D 补偿使能 0x00E0–0x00E7
磁力计 0x004E–0x0055

分组本身不是重点，重点是这张表成了整个系统的契约：下位机和上位机都按它解析数据。任何参数变更必须先改映射表，再改代码，最后改界面。

顺序反过来就会出问题，而且这种错位极难定位——寄存器读出来是个错值，但两边代码各自都“写得对”，你会在界面和固件之间来回找，最后发现契约早就变了。把表当契约，等于把这个排查成本提前消掉了。

完整映射表（每个地址的功能、数据类型、单位、读写方向）见仓库 modbus-register-map.md。

原始数据不能直接用：抖动是怎么来的

ATK-MS901M 通过 USART3 输出九轴数据（陀螺仪、加速度、磁力计、气压计）。这批原始值噪声不小，直接拿去算舵机补偿，结果是舵机在静止状态下持续高频抖动——不是偶尔跳一下，是持续抖，因为补偿把噪声当成了姿态变化在追。

所以下位机跑六通道卡尔曼滤波。但真正花时间的不是滤波器本身，是参数怎么调：

  • 水流条件不同，噪声特性就不同，一套固定参数没法兼顾静水和有流环境；
  • 早期调一次参数要重启下位机，一个来回太久；
  • 因此卡尔曼参数放 RAM，通过 Modbus 实时写入，上位机上拖一下就能立刻看波形变化；
  • 调到满意再发“保存到 Flash”，重启后保留上次校准值。

实时可调 + 可持久化这套链路，比滤波器本身更决定系统能不能用：滤波器是标准件，调参路径才是工程量。

舵机补偿：公式只占一行

8 路舵机各通道独立补偿：

output = BASE + kRoll × roll + kPitch × pitch + kYaw × yaw

公式不难，难的是系数怎么定，以及调试时怎么不被干扰：

  1. BASE 按质心选。 初始 BASE 要结合机器人的质心位置给，否则静止时就带恒定偏置。
  2. k 值分两步标定。 静水中标定，动水中验证——只在静水调好的参数，有流时响应对不上。
  3. 必须能单通道关掉。 补偿使能标志在 0x00E0–0x00E7，每通道独立开关。8 路同时开着时，你分不清是哪一路的 k 值不对；一路一路排除，问题才定位得下来。

BASE 与 k 值存 Flash，可按通道通过 Modbus 调整。标定步骤见仓库 servo-compensation.md。

上位机：为什么坚持浏览器直连

上位机是 React 18 + Vite + TypeScript + TailwindCSS，五个页面覆盖系统、传感器、舵机、外设、高级功能。

选 Web Serial API 而不是「装驱动 + 后台进程 + 桌面程序」，理由很实际：现场调试不该先花时间装环境。浏览器直连串口，打开页面就能用，换台电脑也一样。教学场景下这一点更明显——机房的机器你没法保证装了同一套驱动。

几个细节是被真实问题逼出来的：

  • 自动重连：串口短时断线很常见，不做重连界面就直接报错。现在是最多 10 次指数退避。
  • Mock 模式：URL 加 ?mock 就能在没有硬件时预览，用于演示和无设备时的界面调试。
  • 3D 姿态 + 实时波形：Three.js 显示姿态，图表显示陀螺仪、加速度、磁力计时序，调参时能直接看到滤波效果。
  • ADC 校准面板：每通道增益与偏移可调，结果写回 Flash。

文档不能等做完再写

项目按工程节点分目录：01-硬件设计/、02-下位机固件/、03-上位机软件/、Wiki/。固件按 BSP 驱动组织（ATK_MS901M、Modbus、Kalman、PWM、ADC、Calib、GPIO），上位机按页面、组件、状态管理分层。

Wiki 是开发过程中同步维护的，不是事后补的：system-architecture.md 放整体架构与流程，entities/ 放模块级文档。

寄存器表、引脚分配、补偿标定方法这类内容，写代码的当下顺手记最便宜，事后回忆成本很高。这套“开发即文档”是后面维护和带人都能省时间的地方。

还没做的部分

已实现：姿态采集、舵机补偿、ADC 校准、红外收发。

待实现：PID 姿态闭环、深度传感器与深度控制、ESP32 Wi-Fi 替代有线、水下摄像头、自主导航。这些会逐步补进 Wiki 和寄存器表，让协议层和文档跟着架构一起演进，而不是等架构定型再倒推文档。

结束语

这套系统里最值得复用的不是某个模块，是三条约定：寄存器表当契约、滤波参数运行时可调、上位机不装软件。换到别的嵌入式项目，这三条同样成立。

代码与 Wiki 都在仓库里，可以当类似项目的起点。
