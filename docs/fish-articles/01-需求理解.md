## 早期站点初稿目标（v12）

文章题目定为《Fish 机器鱼平台的搭建流程》。先介绍平台目的和功能，再沿搭建顺序解释系统分工、公网访问与实时视频。Cloudflare Tunnel 和 WebRTC 视频链路是重点，也记录前端选型及维护教训。正文以流程图、框图和紧凑表格承载信息，文字只解释关键结论与边界。文章不展示具体项目效果图或界面截图；具体源码和界面通过 GitHub 仓库查看。中英文同步，保留文章地址、入口和发布状态。

## 早期站点初稿提纲（v12）

1. **平台的目的与功能**：说明机器鱼控制、实时画面、赛事计时与录像、设备管理和固件升级为谁服务，先回答为什么搭建平台。
2. **系统结构与技术分工**：交代浏览器、Go 控制器、ESP32 和 Python 视觉服务的职责，并简述 Go 与 Python 分工的理由。
3. **前端技术选择及维护教训**：说明当前赛事页采用原生 HTML/CSS/JavaScript、管理台采用 React，二者由 Vite 构建。赛事页的大型 HTML 与脚本、分散的样式和外层 iframe 提高维护成本；页面加载与视频首帧要分开分析，不能把慢直接归因于框架。后续方向是拆出控制和视频模块、建立共用样式，再逐步整理或迁移赛事界面；不虚构已经完成的改造。
4. **公网访问**：简要介绍 Cloudflare，讲 Fish 如何用 Tunnel 发布 Go 的页面、API 和 WebSocket 入口。FRP 与自建服务器的详细比较留给现有专题。
5. **实时视频推流（正文重点）**：从相机采集与 Python 画面处理，讲到经 Go 交换 WebRTC 信令、直连及 Cloudflare TURN 中继。说明浏览器从直连阶段开始尝试，失败后才切到仅使用 relay 候选的 TURN 阶段；用视频链路图区分信令与实际媒体路径。
6. **程序怎样选择视频传输路径**：依据源码画出直连 → TURN → 同源 WebSocket JPEG 快照的状态流程，具体解释连接失败、中断、视频轨道结束、解码错误、首帧超时和画面停止更新时的处理。直连失败后尝试 TURN；TURN 未配置或仍失败则进入快照流；快照连接断开后只重连快照流，当前实现不会在该会话中自动升级回 WebRTC。直接访问时的 IP 与子网比较只能提供线索；经 Tunnel 访问时无法据此还原 PC 内网地址。IP 比较没有参与当前选路，切换依据是 ICE 与实际画面。Go 只代理最新 JPEG 帧，避免慢客户端积压旧画面。
7. **赛事功能如何整合**：说明控制、实时画面、计时和录像怎样配合，留下修改相关链路时最重要的提醒。
8. **关键实现边界**：解释设备挑战应答与网页授权、控制权租约及多层停止、OTA 文件完整性与重启后固件身份；以设计对照图辅助今后开发回查。

## 依据与事实边界

- 仓库 `FukunHennan/fish`，固定提交 `134699900e14ad2cbe6eeb0878e1dc55431ceab5`，时间 `2026-10-22T08:27:43Z`。
- 依赖文件、控制权与运动超时实现经本地 blob 与远程目录树比对；细节见 `02-仓库素材与事实核对.md`。
- Go 8081 提供赛事页和 React 管理台，Python API 监听本机 8091；WebRTC/TURN 与同源 JPEG 降级分别画明。
- 赛事页 `competition-adapter.js` 的 `transportStage` 从 `lan` 开始，`retryVideoStream` 将失败的直连切到 `turn`，TURN 失败进入 `startVideoFallback`；`vision/webrtc.py` 分别限制 host 候选或 relay 候选。新会话和切换相机时重置到直连阶段。文章引用这些源码位置，不把界面状态文案当作网络探测结果。
- 实际板型为 ESP32-C3 Super Mini；构建名仍沿用 XIAO。无当前 RGB 或视觉导航能力。
- 控制权关联设备、账号和浏览器；租约、队列运动截止时间、固件连接与心跳检查各有职责。
- 暂停只暂停比赛计时，录像继续且所属战队可操作；录像成功启动才进入比赛。
- 认证是共享部署密钥挑战应答；OTA 区分文件校验、启动、重启后确认。
